# 游戏画面中的离线控制菜单

`start_ingame_control.cmd` 将原生飞机/手动跳伞与白天、**Windows 本机悬浮菜单**组合；用户已确认“白天飞行、跳伞和落地移动都正常”。已确认的白天地面菜单保留在 `start_ingame_ground.cmd`。菜单贴在游戏窗口上，提供天气、武器和吉普车选择，是独立叠加窗口。菜单显示、F6 展开／收起与下拉选择也已实机确认。

## 使用

最新反馈指出飞机横飞、步行后刷新坐标滞留。当前主入口已启用两个修复候选：按航线调整飞机生成旋转，并确认完整移动包的序号、使用最后轨迹点。119项本地测试和原生参数验证通过；新画面和步行刷物效果等待重启验收。此前“正常”确认的范围是白天飞行、离机、落地移动。

1. 退出已有游戏和旧服务，运行 `start_ingame_control.cmd`。需要 Windows、带 Tcl/Tk 的 Python 3.10+，以及自行生成的本地协议材料。
2. 新入口在地图载入阶段生成原生飞机，等待角色就绪与 2 秒登机延迟后沿西→东航线飞行，使用游戏原有离机操作跳伞。菜单开始收起，保留游戏焦点；按 F6 展开或收起。地面入口仍直接从地图地面开始。
3. 首个有效角色位置后 3 秒设置一次正午（12）；登录与环境消息先统一时间基准。地面入口的白天、移动和视角，以及主入口的白天飞行、跳伞和落地移动均已实机确认。昼夜时间与天气独立，不会覆盖手动选择的天气。
4. “天气”可选择 24 个原生状态和 0–600 秒过渡。“武器”可选 20 种枪械、1–5 把、0–999 发匹配弹药及刷新距离。“载具”可在附近刷新四座吉普车，每轮最多 16 辆。请落地后刷新武器和载具，乘坐飞机时服务会拒绝刷物。
5. 点击操作后等待回执，再收起菜单返回游戏。武器在附近地面生成，需要使用游戏原有拾取交互。

只连接本轮服务的本地文件邮箱，不启动 HTTP、不打开浏览器、不修改客户端文件，也不访问游戏内存或注入 DLL。菜单随窗口位置调整；游戏最小化或切到其他应用时隐藏。服务结束时关闭其菜单子进程；游戏窗口消失超过 5 秒时菜单自行退出。新增组合入口与地面入口都使用独立测试会话；原稳定 `start_offline_parachute.cmd` 保持原配置。

“已发送”表示数据已进入游戏连接；它不等于已目视确认天气变化、物品拾取或驾驶。本轮真实会话已接收一条菜单吉普车命令并发送车辆数据；天气视觉、完整拾取及驾驶仍需分别验收。

## 输入和窗口修复

- 部分游戏输入模式未向菜单交付 `WM_HOTKEY`，增加仅针对 F6 的键状态检测，并对两路事件去重；保留鼠标按钮。修复后用户确认 F6 正常。
- 状态刷新曾每 200 毫秒执行 `wm deiconify`，使下拉框闪退。现在仅在窗口确实隐藏时显示，且下拉展开期间不改变位置和显示状态。用户确认下拉和选择恢复正常。
- 不在定时刷新中反复重置按钮状态，避免干扰鼠标操作。
- 菜单新增服务器收到的当前位置（米）；步行后可以用F6核对坐标是否变化。刷新记录在服务日志中带有实际使用的角色坐标。
- 独立界面预览：`python ingame_overlay.py --preview`。预览按钮禁用，不连接游戏。

## 服务与验证

早先只延迟正午设置仍导致卡死：旧登录样本服务器时间为 0，后续时钟为真实 epoch。原生回调模拟复现约负 17 亿秒的异常偏移。现在只在发送时同步登录时间，不写原始样本，再发送正午时钟。使用世界样本设置昼夜时，必须明确 `--world-time-tail-bytes` 布局；本入口使用经过原生验证的历史 18 字节尾部。修正后的地面白天与主入口的白天飞行、跳伞、落地移动均获用户实机确认。天气视觉切换、完整拾取及驾驶仍需各自验收。

`--ingame-overlay` 创建本轮 `IngameMailbox`，再启动菜单子进程。`MailboxClient` 校验状态、限定整数参数和递增序号，并等待上一操作回执。游戏线程调用现有 `ControlSession`，使用本轮 TPDU/AES 密钥发送消息。退出、未就绪、乘车、刷物数量上限等检查仍在服务端执行。

7 项专项测试覆盖文件指令校验、重放/部分行、客户端文件保护，以及 Lua 实验和悬浮菜单入口的真实加密回复。新增组合检查从同步登录、飞机西侧起点/登机、正午、手动离机、地面位置一直到天气/武器/吉普车操作；吉普车使用地面坐标而不是飞行高度。悬浮入口不安装客户端文件。测试使用合成状态，不运行 Windows 界面引擎；画面与交互需要实机确认。

```powershell
python -m unittest test_ingame_bridge test_ingame_session -v
```

## 保留的原生 Lua 加载研究：实机失败

`start_ingame_lua_probe.cmd` 保留原试验。它尝试 `ScriptCustom`、`-useallfiles` 与自有 `LoadConfig.lua`，复用原 `EuReportWindowPanel` 六选项面板。两轮实机都进入地图，但用户确认没有菜单或按钮，且没有生成 `loader.log/LUA_ENTER` 正向标记。不能宣称原生 Lua 菜单已接入。`~` 出现命令框的反馈是用户误选，已明确更正为没有出现。

`ingame/RoeControlPanel.lua` 与 `bootstrap.lua` 仅通过 Lua 5.1 模拟。只读分析确认 `/lua` 和 `_GM_CONTROL_` 存在，不证明调试入口可用，也不证明某个快捷键。

Lua 试验运行期间仅新增四个自有文件：根目录和 `Data/ScriptCustom` 下的 `ROE_OfflineMenu.lua`、`Data/ScriptCustom/LoadConfig.lua`、缺失时的 `FileDriven/_GM_CONTROL_`。已有文件碰撞拒绝，原 EXE/DLL/SFC 不改动。服务正常结束只清理本轮创建且哈希匹配的文件；用户修改的文件保留。若异常中断，退出游戏后按本轮收据清理：

```powershell
python ingame_bridge.py cleanup private/ingame-control/session-实际目录/installed-files.json
```

当前悬浮菜单入口不需要安装或清理这些文件。
